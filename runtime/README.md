# HASLAB runtime

The runtime area contains a minimal Python lifecycle for the pinned M6 graph package. It strictly parses the proposed `.hxb` framing, verifies section hashes and zero padding, rejects duplicate JSON keys and incompatible manifests, allocates declared external buffers, applies only validated DMA relocations, binds an exact-size input, submits commands to `haslab_sim`, and returns a generation-scoped completion token with structured device faults. The complete accelerator package executes 412,092 commands through nodes 0–217 and emits three raw INT32 HWC8 learned-head tensors. Diagnostic mode exposes comparison boundaries; release mode reuses output storage and exposes the three final tensors.

`haslab_runtime.SimulatorRuntime` provides `load_model`, `bind_input`, `submit`, `wait`, and `reset`. It records accepted commands, FIFO `BUSY` responses, commands retired while refilling, high-water mark, and final drain. Unit tests cover bit-exact compiler-to-simulator execution, corrupt-package rejection, binding size, and stale-token invalidation.

`haslab_runtime.unpack_boundaries`, `decode_host_tail`, and `select_detections` implement the pinned YOLOv8n host path: per-channel INT32 dequantization, ONNX nodes 218–260, letterbox reversal, confidence filtering, and class-aware NMS. The [host-tail report](../benchmarks/manifests/yolov8n-320-opset13/m6-host-tail.json) compares the decoder with an independently executed ONNX tail on one synthetic accelerator output. This remains a synchronous Python research backend, not the planned C ABI, FPGA driver, general model runtime, or measured COCO command path.
